# Docker Principles and Container Runtime

## 1. Overview

This document describes the containerization workflow implemented in this repository, using a Java 21 application as the workload.

The objective is to demonstrate practical knowledge of Docker image construction, container execution, runtime configuration and container lifecycle management.

The implementation follows a reproducible workflow: compile the Java application, package it as an executable JAR, build a Docker image and run the resulting container.

## 2. Application Architecture

The initial workload is a standalone Java 21 application.

**Technology stack**

- Java 21 (Eclipse Temurin)
- Eclipse Temurin 21 JRE
- Docker Engine
- Linux-based container environment

**Application characteristics**

- Executable Java application packaged as a JAR.
- Runtime configuration through environment variables.
- No dependency on the host Java runtime once containerized.
- Explicit container entry point.

## 3. Java Application Build

The application is compiled using the Java 21 compiler.

```bash
javac -d out src/main/java/com/lab/docker/DockerHelloApp.java
```

The generated bytecode is packaged into an executable JAR:

```bash
jar --create --file app.jar --main-class com.lab.docker.DockerHelloApp -C out .
```

The resulting artifact can be executed independently:

```bash
java -jar app.jar
```

This separates application compilation from runtime execution.

## 4. Docker Image Definition

The Dockerfile defines the runtime environment and the application startup command.

```dockerfile
FROM eclipse-temurin:21-jre

WORKDIR /app

COPY java-app/app.jar app.jar

ENV APP_ENV=development

ENTRYPOINT ["java", "-jar", "app.jar"]
```

**Design decisions**

| Instruction | Purpose |
|---|---|
| `FROM` | Uses Eclipse Temurin 21 JRE as the runtime base image. |
| `WORKDIR` | Establishes `/app` as the working directory. |
| `COPY` | Transfers the executable JAR into the image. |
| `ENV` | Defines the default application environment. |
| `ENTRYPOINT` | Specifies the container's main process. |

Using a JRE instead of a JDK avoids including development tools that are unnecessary at runtime.

## 5. Image Construction

The Docker image is built from the module directory:

```bash
docker build -t docker-hello:1.0 .
```

The command defines:

- Image name: `docker-hello`
- Image tag: `1.0`
- Build context: current directory

The build process resolves the base image, applies the Dockerfile instructions and produces a locally available image.

To inspect the resulting images:

```bash
docker images
```

The generated image is identified as `docker-hello:1.0`.

## 6. Container Runtime Execution

A container is created and started from the image:

```bash
docker run --name docker-hello-test docker-hello:1.0
```

The container executes the Java application through the configured entry point.

The application prints its runtime information and terminates successfully.

## 7. Container Lifecycle Inspection

Container state can be inspected using:

```bash
docker ps -a
```

The observed result is:

```text
STATUS: Exited (0)
```

Exit code `0` indicates successful process termination.

This behaviour illustrates a fundamental Docker principle: a container remains running while its primary process is running. When that process terminates, the container transitions to the `Exited` state.

The container lifecycle is therefore directly tied to the lifecycle of its main process.

## 8. Runtime Configuration

The application reads its environment configuration through the `APP_ENV` variable.

When no explicit value is provided, the application uses `development` as its default.

The same application was also executed with an alternative environment value:

```bash
APP_ENV=container-test java -cp out com.lab.docker.DockerHelloApp
```

This demonstrates configuration through environment variables without modifying application source code.

The next stage will verify the same configuration mechanism directly through Docker.
